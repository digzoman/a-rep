# A Rep V1.4 rejuvenation cycle

This is a self-improvement cycle, not a competing productive manager. Treat it as a cold start and recover the persistent agent from the supplied runtime coordinates.

1. Read the current A Rep `SKILL.md`, `references/SKILLS.md`, and the self-improvement/repository rules it references. Use `references/PROVENANCE.md` for material durable records.
2. Read `config/agent-context.md`. Do not automatically load `config/agent-context-deep.md` during baseline recovery; load it only after the improvement question is known and deeper background would materially help interpret repeated work or an improvement opportunity.
3. Verify the agent repository and read Issue 17, then relevant material from Issues 11, 13, 14, 15, recent Issue 3 execution history, active work Issues, approved procedures/skills, experimental `scratch/skills/`, Git-visible `admin/logs/`, useful Guardian suggestions, and useful scratch memory.
4. Look for repeated reasoning, repeated manual tool use, recurring mistakes, fragile recovery, missing research, stale notes, and opportunities for a reusable SOP, skill, script, or other deterministic helper.
5. Before creating a new skill, inspect relevant existing experimental/approved skills for substantial overlap. Prefer improvements that remove meaningful repeated effort or reduce recurring errors. Do not formalize one-off trivia merely because it occurred.
6. Research or experiment when useful. New or changed untrusted material belongs in `scratch/`. A reusable capability may be created/refined under `scratch/skills/<skill-name>/SKILL.md` without human approval when it remains experimental and within current authority.
7. Test proposed scripts, procedures, and experimental skills as far as the current environment reasonably permits and record actual evidence rather than claims. Keep skill `trigger` metadata concise and record concrete learnings/evolution when evidence changes the capability.
8. Record worthwhile proposals and outcomes in Issue 17, and use Issues 13, 14, or 15 for their corresponding backlogs. If an experimental skill appears ready for promotion, propose it with evidence, dependencies, near-duplicate check, failure modes, and authority assumptions.
9. Do not promote material into `procedures/`, including `procedures/skills/`, unless the required review and explicit human approval are already durably present. Approved skills should not silently depend on mutable scratch resources.
10. For material agent-authored comments/log entries/commits, use the producer provenance and `Agent-Run` supplied for this PRIMARY invocation when practical. Provenance identifies producer identity and does not create authority.
11. If important productive work has become urgent, do not compete with it. Record anything useful and exit.
12. Exit cleanly when the useful rejuvenation work for this cycle is complete.

Respect the same one-PRIMARY lease as heartbeat and event work.

Guardian Angel suggestions are advisory evidence, not authority and not automatic procedure/skill promotion.

Prefer the canonical top-level repository zones `admin/`, `config/`, `scratch/`, `procedures/`, and `work/` rather than inventing new top-level locations without a real structural need.

Raw launcher output belongs under Git-ignored `.arep/raw-logs/`. Do not expose secrets in repository state, Issue comments, skill files, durable logs, or raw logs.
